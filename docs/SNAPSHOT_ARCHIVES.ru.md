Команда `d8 snapshot download` скачивает снимок из кластера в директорию, а `d8 snapshot upload` загружает его из
этой директории. Формат архива общий для `d8` и веб-интерфейса Deckhouse. Команды в примерах относятся к `d8`.
Внешняя система может создавать или хранить архив в том же формате.

Формат архива не требуется [для создания снимка](user_guide.html#создание-снимка),
[проверки его состояния](user_guide.html#отслеживание-статуса) или передачи данных [через
API интеграции](backup_integration.html). Он необходим, когда снимок передаётся в виде файла для использования
инструментами Deckhouse Platform. Формат позволяет:

- передавать снимок через файловое хранилище или на физическом носителе;
- не связывать внешнюю систему и кластер сетью;
- не требовать их одновременной работы.

При использовании другого формата обмен снимками возможен только через собственные HTTP-запросы к API узлов, описанному
[в разделе «Структура снимка и API узлов»](backup_integration.html#структура-снимка-и-api-узлов).

Эта спецификация описывает дерево директорий и его упаковку в файл `.zip`. Наличие формата упаковки не означает, что
каждый клиент принимает ZIP-файлы. Команда `d8 snapshot upload -i` принимает только распакованную директорию, а не
ZIP-файл. Перед загрузкой через `d8` распакуйте ZIP-архив.

## Порядок сборки

Собирайте архив от дочерних узлов к корню, чтобы контрольные суммы дочерних узлов были известны до формирования
метаданных родительского узла. Для этого выполните следующие шаги:

1. Разложите дерево: по директории на узел, прямые дочерние узлы — в `snapshots/`.
1. Разместите в каждом узле его манифесты и, если у узла есть том, единственный файл данных.
1. Заполните в каждом `snapshot.yaml` всё, кроме контрольных сумм.
1. Посчитайте у каждого узла `checksum`.
1. **Начиная с дочерних узлов**, вычислите `childrenChecksum`, затем `metadataChecksum`, и запишите `snapshot.yaml`.
   Порядок важен, потому что контрольные суммы дочернего узла входят в контрольную сумму родительского узла.
1. Проверьте директорию: `d8 snapshot local describe <DIRECTORY>`.
1. Если нужен один файл — упакуйте проверенное дерево в `.zip`.

## Дерево

Верхний уровень содержит ровно одну директорию. Её имя может быть любым. Это директория корневого узла. Каждый узел, и
корень, и потомок, — директория одной и той же формы:

```text {.nowrap-default}
my-namespace-snapshot/                      # Корневой узел.
├── snapshot.yaml                           # Описание узла и три его контрольные суммы.
├── manifests/                              # Собственные манифесты узла, по файлу на объект.
│   └── configmap_app.yaml
└── snapshots/                              # Прямые дочерние узлы. У узла без дочерних узлов директории нет.
    ├── volumesnapshot_data-0/              # Узел VolumeSnapshot с блочным томом.
    │   ├── snapshot.yaml
    │   ├── manifests/
    │   │   └── persistentvolumeclaim_data-0.yaml
    │   └── data.bin
    └── volumesnapshot_files-0/             # Узел VolumeSnapshot с файловым томом.
        ├── snapshot.yaml
        ├── manifests/
        │   └── persistentvolumeclaim_files-0.yaml
        └── data.tar
```

**При сборке архива соблюдайте следующие требования:**

- Размещайте файл `snapshot.yaml` в каждом узле. Если `snapshot.yaml` отсутствует в корневом узле, при загрузке
  отклоняется весь архив.
- Сохраняйте в директории `manifests/` без изменений все объекты из массива, который
  [`manifests-download`](backup_integration.html#чтение-манифестов-узлов) вернул для этого узла, и только их. Каждый
  объект сохраняйте в отдельном файле. Директория `manifests/` должна присутствовать в каждом узле и не может быть
  пустой: у узла Snapshot неймспейса в ней находится как минимум манифест Namespace, а у узла VolumeSnapshot — один манифест
  захваченного PersistentVolumeClaim (PVC). При загрузке это требование не проверяется: узел без манифестов
  принимается без сообщения об ошибке.
- Используйте для файлов манифестов имена, оканчивающиеся ровно на `.yaml`. Файлы с расширением `.yml` или другим
  суффиксом не считаются манифестами: они не входят в `checksum`, не загружаются и игнорируются без сообщения об ошибке.
  Эти файлы также не попадают в список пропущенных файлов, который показывается после обхода.
- Используйте уникальные имена файлов внутри `manifests/`. Обычно достаточно схемы на основе `kind` и имени объекта, но
  одинаковый `kind` может встречаться в разных API-группах. `d8` использует имя
  `<KIND>_<NAME>.yaml`, а если такой `kind` есть в нескольких API-группах, добавляет группу:
  `<KIND>.<GROUP>_<NAME>.yaml`.
- Каждый файл манифеста должен содержать ровно один непустой YAML- или JSON-документ. Не используйте второй документ
  после `---`, пустые документы или повторяющиеся ключи в одном mapping: при загрузке манифест разбирается как
  структурированный документ, а не переносится как последовательность байтов.
- Не переименовывайте файл манифеста после подсчёта `checksum`: относительный путь файла входит в контрольную сумму.
- Размещайте каждый прямой дочерний узел в отдельной поддиректории `snapshots/`. Если у узла нет дочерних узлов,
  директория `snapshots/` не создаётся. Тип дочернего узла определяется только по его `snapshot.yaml`: имя поддиректории
  не несёт смысла, но должно быть уникальным среди соседних узлов. `d8` использует схему
  `<KIND>_<NAME>`, а при совпадении имени добавляет `__<CHECKSUM_PREFIX>`.
- Не размещайте в одном узле больше одной полезной нагрузки (Payload): `data.bin`, `data.bin.zst` или `data.tar`.
  Требования описаны [в разделе «Полезная нагрузка тома»](#полезная-нагрузка-тома).
- Не создавайте директорию `data/`: она интерпретируется как узел с несколькими томами, а такие узлы отклоняются.

**При чтении архива, созданного другой реализацией, не определяйте объекты и узлы по именам.** Объект определяется
только содержимым манифеста, а узел в поддиректории — только его `snapshot.yaml`.

Поддиректория `snapshots/` без этого файла не считается дочерним узлом: она пропускается без ошибки и попадает в список
пропущенного, который показывается после обхода.

При этом архив всё равно будет отклонён, если этот дочерний узел учтён в `childrenChecksum` родительского узла:
контрольная сумма перестанет совпадать. Поэтому удалить узел из готового дерева, удалив только его `snapshot.yaml`,
нельзя.

Директории `data.bin.d/`, `data.tar.d/` и файл `identity.json` остаются после незавершённого скачивания инструментами
Deckhouse Platform и на содержимое узла не влияют.

Дополнительные данные игнорируются без сообщения об ошибке и не попадают в отчёт. Это относится, например, к неизвестным
полям в `snapshot.yaml` и посторонним файлам в директории узла. Поэтому передавать через них собственные данные нельзя.

Исключение составляют имена, зарезервированные для полезной нагрузки: `data.bin*`, `data.tar` и `data`. Файлы и
директории с такими именами всегда считаются частью полезной нагрузки и проверяются строго: лишний файл с таким именем
или некорректное содержимое может привести к отклонению узла. Файл, имя которого лишь начинается с `data.tar`, например
`data.tar.zst`, не является полезной нагрузкой: он игнорируется без сообщения об ошибке, поэтому не сжимайте полезную
нагрузку файлового узла.

**Следующие нарушения приводят к отклонению всего архива до обращения к кластеру:**

| Нарушение | Правило |
|---|---|
| Корень не является снимком неймспейса | При загрузке архива целиком корневой узел должен содержать `apiVersion: state-snapshotter.deckhouse.io/v1alpha1` и `kind: Snapshot`. Если корнем является VolumeSnapshot, возвращается ошибка `archive root VolumeSnapshot/<NAME> is not a core Snapshot`. Это ограничение режима загрузки, а не формата архива |
| Узел VolumeSnapshot без данных тома | Узел с `apiVersion: snapshot.storage.k8s.io/v1` и `kind: VolumeSnapshot` должен содержать одну из полезных нагрузок: `data.bin`, `data.bin.zst` или `data.tar` |
| `volumes` не соответствует полезной нагрузке | Если полезная нагрузка присутствует, поле `volumes` должно содержать ровно одну описывающую её запись. Если полезной нагрузки нет, `volumes` не должно содержать записей. Более одной записи у одного узла быть не может |

**Один том можно загрузить отдельно, указав узел.** Требование к корневому узлу относится только к загрузке архива
целиком.

Любой узел VolumeSnapshot из архива можно загрузить отдельно, если указать целевой узел. В `d8` это делается флагом
`--node`:

```shell
d8 snapshot upload -n <NAMESPACE> -i <DIRECTORY> --node VolumeSnapshot/<NODE_NAME>
```

где:

- `<NAMESPACE>` — неймспейс, в который загружается том;
- `<DIRECTORY>` — путь к директории архива;
- `<NODE_NAME>` — имя узла VolumeSnapshot в архиве.

Проверки `snapshot.yaml`, полезной нагрузки и контрольных сумм выполняются так же, как при загрузке архива целиком.

Узел создаётся в кластере **как новый самостоятельный объект**, присоединить его к уже существующему дереву нельзя.

Команда проверяет контрольные суммы предков выбранного узла по `snapshot.yaml`. Она не ищет эти объекты в кластере и
не создаёт их.

## Полезная нагрузка тома

Узел содержит не более одной полезной нагрузки. Поле `volumes` в `snapshot.yaml` должно соответствовать ей:

| Узел | Полезная нагрузка | `volumes` |
|---|---|---|
| Без тома | нет | Поле отсутствует или содержит `[]`, оба варианта равнозначны |
| Блочный том | `data.bin` или `data.bin.zst` | ровно одна запись, `volumeMode: Block` |
| Файловый том | `data.tar` | ровно одна запись, `volumeMode: Filesystem` |

Узлу VolumeSnapshot доступны только две последние строки. Пустой список `volumes: []` не влияет на `metadataChecksum`,
поскольку исключается из канонической формы так же, как отсутствующее поле.

**Блочный том.** Для несжатой полезной нагрузки используется `data.bin`. Файл содержит всё блочное устройство в том
виде, в котором его вернул экспорт. Для сжатия с помощью zstd используется `data.bin.zst`. Другие алгоритмы сжатия не
поддерживаются.

Для блочного узла размер полезной нагрузки записывается в `snapshot.yaml` в поля `rawSizeBytes` и `storedSizeBytes`,
описанные [в разделе «Файл `snapshot.yaml`»](#файл-snapshotyaml). Значение `size` — номинальная ёмкость тома, с полезной
нагрузкой оно не сравнивается: полезная нагрузка может быть больше `size`, поскольку система хранения может округлять
выделенный том вверх. Как определить значение `size`, описано [в разделе «Размер тома»](backup_integration.html#размер-тома).

При загрузке полезная нагрузка сверяется с записанными размерами. Для `data.bin` размер файла должен быть равен
`storedSizeBytes`. Для `data.bin.zst` сумма объявленных размеров фреймов должна быть равна `rawSizeBytes`, а
распакованное содержимое — иметь ровно такую длину. Расхождение даже на один байт приводит к отклонению архива. Если поле
размера отсутствует, `d8` измеряет полезную нагрузку сам. Создаваемый том должен быть не меньше полезной нагрузки, иначе
загрузка завершается ошибкой.

**Файловый том.** Для файлового тома размер полезной нагрузки не соответствует ёмкости тома. При загрузке размер
полезной нагрузки берётся из заголовков записей `data.tar`, а `rawSizeBytes` и `storedSizeBytes` не используются.

### Правила потока zstd

Эти правила одинаковы для `data.bin.zst` и для сжатых записей внутри `data.tar`:

- каждый фрейм объявляет свой `Frame_Content_Size`;
- пропускаемые фреймы и словарь не используются;
- структура всех фреймов не нарушена;
- сумма объявленных размеров равна `rawSizeBytes` из `snapshot.yaml`, а для записи внутри `data.tar` — её собственному
  `D8.snapshot.fs.rawSize`.

**Несколько фреймов упрощают возобновление переноса.** Прерванные скачивание и загрузка продолжаются с нужного смещения
в несжатых данных. Найти это смещение в сжатом файле можно только по заголовкам фреймов. Объявленные размеры позволяют
определить их границы, поэтому достаточно распаковать нужный фрейм, а не весь поток от начала до места обрыва.

Один фрейм на весь том допустим, но при каждом возобновлении поток придётся распаковывать с начала. Размер фрейма
контрактом не задаётся.

{{< alert level="warning" >}}
При передаче данных компрессору через конвейер, например `cat data.bin | zstd`, компрессор не знает размер входных
данных заранее и не записывает `Frame_Content_Size`.

Передавайте компрессору файл напрямую, например с помощью `zstd data.bin`. В этом случае размер известен и записывается
в заголовок фрейма.
{{< /alert >}}

Фреймы проверяются при загрузке. Часть требований проверяется до начала передачи данных, часть — уже во время переноса.
При нарушении любого из них загрузка завершается ошибкой.

Полезная нагрузка, сжатая через конвейер, при этом проходит проверку
[трёх контрольных сумм](#как-считаются-контрольные-суммы) и `d8 snapshot local describe`: данные на диске не повреждены,
но их размер нельзя определить по метаданным фреймов.

### Файловый том — data.tar

Сам `data.tar` не сжимается, сжимать можно только отдельные записи внутри него. Содержимое `data.tar` также определяется
форматом архива.

При экспорте файлового тома файлы скачиваются по отдельности, поэтому `data.tar` формирует система, создающая архив.
Обычный tar-архив из скачанных файлов не подходит, без описанных ниже служебных записей он будет отклонён.

Каждая запись обычного файла несёт три PAX-записи:

| PAX-запись | Значение |
|---|---|
| `D8.snapshot.fs.codec` | Кодек записи — `none` или `zstd`. Все записи в `data.tar` должны использовать один и тот же кодек. `data.tar` со смешанными кодеками отклоняется |
| `D8.snapshot.fs.originalPath` | Относительный нормализованный путь файла внутри тома |
| `D8.snapshot.fs.rawSize` | Размер записи до сжатия в байтах. Значение указывается десятичным числом без ведущих нулей. Для `none` оно должно точно совпадать с размером записи в `data.tar`. Для `zstd` — с размером данных после распаковки |

Требования к пути в `D8.snapshot.fs.originalPath`:

- Не должно быть ведущего `/`, обратного слеша `\` и буквы диска.
- Не допускаются пустые сегменты, а также сегменты `.` и `..`.
- Не допускаются символы с кодом ниже `0x20` и символ `0x7f`.
- Первый сегмент не должен быть `.d8-meta`.
- После нормализации сегментов `.` и `..` путь не должен изменяться.

**Имя файловой записи определяется `originalPath` и кодеком.** Для `none` используется сам `originalPath`, для `zstd` к
нему добавляется `.zst`. Значение `originalPath` должно быть уникальным среди записей обычных файлов: две записи с
одинаковым путём отклоняются.

Дополнительные PAX-поля, кроме трёх описанных выше, разрешены, но не интерпретируются и не имеют гарантированной
семантики.

**Директории передаются обычными записями директорий без PAX-полей.** К их именам применяются те же требования, что и к
`originalPath`, кроме завершающего `/`. Поэтому команда `tar -C /volume -cf data.tar .` не подходит: она создаёт записи
`./`, `./sub/` и далее, которые отклоняются из-за сегмента `.`. Формируйте имена от корня тома без ведущего `./`.

**Порядок записей в `data.tar` не имеет значения.** Явно добавлять родительские директории не требуется. Например,
запись `a/b/file` принимается и без записей `a/` и `a/b/`: недостающие директории создаются при записи файла.

**Для обычных файлов восстанавливаются `mode`, `mtime` и числовые `uid` и `gid`.** Имена владельца и группы (`uname` и
`gname`), а также атрибуты директорий не переносятся.

Даже для явной записи директории права, владелец и время не восстанавливаются. Директория создаётся как родитель для
находящегося в ней файла, а остальные атрибуты записи не используются.

**Записи, которые не являются обычными файлами или директориями, отклоняются.** К ним относятся символические ссылки,
жёсткие ссылки, устройства и именованные каналы (FIFO). Пустые директории также отклоняются, поскольку протокол загрузки
переносит файлы и не может воссоздать директорию, в которой нет файлов.

Чтобы пропустить неподдерживаемые элементы, необходимо явно разрешить их пропуск. По умолчанию он отключён. В `d8`
для этого используется флаг `--skip-unsupported-fs-entries`. Пропущенные элементы перечисляются после загрузки,
поскольку их отсутствие означает потерю данных в восстановленном томе.

{{< alert level="info" >}}
Исключение — пустая директория `lost+found`. Она всегда пропускается без дополнительного разрешения и не считается
потерей данных. Такая директория создаётся при разметке файловой системы ext4 и в исправном томе остаётся пустой. Без
этого исключения ни один том ext4 нельзя было бы загрузить без разрешения пропуска. Проверяется последний сегмент пути,
поэтому исключение действует на любой глубине, а не только в корне тома.
{{< /alert >}}

## Файл snapshot.yaml

Файл `snapshot.yaml` описывает узел и содержит данные для проверки его содержимого. Он проверяется до первой записи в
кластер. Если проверка `snapshot.yaml` завершается ошибкой, весь архив отклоняется.

Пример файла `snapshot.yaml` узла VolumeSnapshot:

```yaml
formatVersion: 3
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
name: data-0
namespace: my-app
uid: 5f6bd1ca-2c1a-4a2f-9f3f-000000000001
checksum:
  algorithm: sha256
  hex: 311996ce65e34f57fb9748e53a35c1f31df523ed533436ebce32a13f02f0f984
  short: 311996ce
childrenChecksum:
  algorithm: sha256
  hex: 926e82507890b7d5c7ad50f8cb7fd2172f81bfd2cf1d2ca86e3b644f66b02701
  short: 926e8250
metadataChecksum:
  algorithm: sha256
  hex: bc79311efba6b6048e0a3f8434b2b6e1b29b904eed144934067d412d6b9b8424
  short: bc79311e
volumes:
  - target:
      apiVersion: v1
      kind: PersistentVolumeClaim
      name: data-0
      namespace: my-app
      uid: 5f6bd1ca-2c1a-4a2f-9f3f-000000000002
    artifact:
      apiVersion: snapshot.storage.k8s.io/v1
      kind: VolumeSnapshotContent
      name: snapcontent-1
    volumeMode: Block
    storageClassName: my-storage-class
    size: 10Gi
    rawSizeBytes: 10737418240
    storedSizeBytes: 10737418240
```

**Пишите простые YAML-скаляры и не включайте поля без значений:**

- Указывайте `formatVersion`, `rawSizeBytes` и `storedSizeBytes` **числами без кавычек**: `formatVersion: 3`, а не
  `"3"`.
- Необязательное поле без значения **не включается в файл**. Не записывайте его как `null`, `~` или пустую строку.
  `metadataChecksum` рассчитывается по канонической форме файла, в которой поля без значений отсутствуют. Поэтому явно
  указанное `null` не воспроизводит контрольную сумму, и архив отклоняется.
- Порядок ключей не имеет значения: контрольные суммы покрывают значения полей, а не сам YAML-документ.

| Поле | Наличие | Правило |
|---|---|---|
| `formatVersion` | Обязательно для новых архивов | Значение — `3`. Архивы со значением `2` тоже принимаются |
| `apiVersion`, `kind`, `name` | Обязательно | Идентичность объекта узла. Для Snapshot и VolumeSnapshot также определяет обязательное содержимое узла |
| `namespace`, `uid` | Необязательно | Дополнительные поля идентичности. Их значения участвуют в расчёте `childrenChecksum` родительского узла |
| `sourceName`, `sourceObjectRef` | Необязательно | Сведения об исходном объекте. `sourceObjectRef` либо содержит `apiVersion`, `kind` и `name`, либо отсутствует целиком |
| `checksum`, `childrenChecksum`, `metadataChecksum` | Обязательно | Контрольные суммы содержимого узла, прямых дочерних узлов и самого `snapshot.yaml` |
| `volumes` | Зависит от полезной нагрузки | Описывает полезную нагрузку тома. Правила приведены [в разделе «Полезная нагрузка тома»](#полезная-нагрузка-тома) |

**`formatVersion`.** Текущая версия — `3`, `d8` записывает её начиная с версии 0.33.16. Версия `3` отличается от версии
`2` только полями `rawSizeBytes` и `storedSizeBytes` в записи `volumes`. Архив версии `2` принимается: размер полезной
нагрузки при загрузке измеряется. Архив с любым другим `formatVersion` не принимается. Файл без `formatVersion` относится к формату, использовавшемуся до введения версионирования. Целостность его
метаданных не защищена. Не создавайте новые архивы без `formatVersion`. По умолчанию команды `d8 snapshot upload` и
`d8 snapshot local describe` отклоняют такие архивы. Параметр `--allow-unauthenticated-legacy` допускает просмотр или
импорт только доверенных старых архивов, но не позволяет отличить действительно старый архив от изменённых метаданных.

**`apiVersion`, `kind`, `name`, `namespace`, `uid`.** У дочернего узла `apiVersion`, `kind` и `name` должны совпадать
со значениями в ссылке родительского узла. Для корневого узла используются значения самого узла: Snapshot для снимка
неймспейса, VolumeSnapshot или доменного вида для снимка отдельного ресурса или выбранного поддерева.
Манифест Namespace принадлежит только узлу Snapshot неймспейса. Ограничение `d8 snapshot upload` при загрузке целого
архива описано [в разделе «Дерево»](#дерево). Если указаны `namespace` и `uid`, их значения должны совпадать с теми,
по которым рассчитан
`childrenChecksum` родительского узла. Требования к содержимому узлов Snapshot и VolumeSnapshot приведены [в разделе
«Дерево»](#дерево), а алгоритм расчёта `childrenChecksum` — [в разделе
«Как считаются контрольные суммы»](#как-считаются-контрольные-суммы).

**`sourceName`, `sourceObjectRef`.** `sourceName` содержит имя захваченного исходного объекта, а `sourceObjectRef` —
его `apiVersion`, `kind` и `name`. При самостоятельной сборке архива эти поля можно не указывать. Если архив создан
инструментами Deckhouse Platform и загружается повторно, сохраняйте их без изменений: значения входят в
`metadataChecksum`.

**`checksum`, `childrenChecksum`, `metadataChecksum`.** `childrenChecksum` указывается и для узла без дочерних узлов.
Все три контрольные суммы имеют одинаковый формат:

- `algorithm` — `sha256`;
- `hex` — 64 символа hex в нижнем регистре;
- `short` — первые 8 символов `hex`.

Запись `volumes` описывает том из полезной нагрузки. На основе этой записи при загрузке создаётся DataImport:

| Поле | Правило |
|---|---|
| `target` | Сведения, идентифицирующие захваченный PVC: `apiVersion`, `kind` и `name` обязательны, а `namespace` и `uid` соответствуют PVC. Манифест этого PVC находится в `manifests/` этого узла |
| `artifact` | Сведения о сохранённом контенте, к которому узел был привязан на момент захвата |
| `volumeMode` | Поле обязательно. Для `data.bin` и `data.bin.zst` укажите именно `Block`, а для `data.tar` — `Filesystem`. Пустое или другое значение считается несоответствием полезной нагрузке |
| `storageClassName` | Поле обязательно и не должно быть пустым |
| `size` | Ёмкость захваченного тома |
| `rawSizeBytes` | Размер несжатой полезной нагрузки в байтах. Для `data.bin` и `data.bin.zst` — длина данных блочного устройства, для `data.tar` — сумма `D8.snapshot.fs.rawSize` по его записям обычных файлов |
| `storedSizeBytes` | Размер файла полезной нагрузки на диске в байтах: `data.bin`, `data.bin.zst` или `data.tar` |

Для `artifact` поля `apiVersion`, `kind` и `name` обязательны и не должны быть пустыми. Например, для узла
VolumeSnapshot указывается VolumeSnapshotContent из `status.boundVolumeSnapshotContentName`. Значения этих полей при
загрузке не сверяются и не используются. `artifact` имеет ту же структуру, что и `target`, поэтому `namespace` и `uid`
также разбираются и входят в `metadataChecksum`. Для кластерного содержимого `namespace` и `uid` не указывайте.

Значение `size` обязательно и должно быть положительным. При сборке архива из Snapshot в кластере берите его из
`status.data.size` узла тома, а не из `PersistentVolumeClaim.spec.resources.requests.storage` в манифесте.
Полные правила передачи размера приведены [в разделе «Размер тома»](backup_integration.html#размер-тома).
Дополнительные требования для блочного узла описаны [в разделе
«Полезная нагрузка тома»](#полезная-нагрузка-тома).
При загрузке `size` определяет размер создаваемого тома, поэтому оно не должно быть меньше ёмкости захваченного тома.

Записывайте `rawSizeBytes` и `storedSizeBytes` для каждого узла с полезной нагрузкой. Нулевое значение не записывается.
При загрузке эти поля не обязательны: если поле отсутствует, `d8` измеряет полезную нагрузку. Для файлового узла `d8` при
загрузке их не использует, поскольку размер полезной нагрузки берётся из заголовков записей `data.tar`.

## Как считаются контрольные суммы

Все три контрольные суммы рассчитываются с помощью SHA-256. Ниже приведён точный алгоритм, по которому инструменты
рассчитывают и проверяют контрольные суммы.

**`checksum` — контрольная сумма содержимого узла.** При расчёте учитываются все файлы `manifests/*.yaml` и единственная
полезная нагрузка (`data.bin`, `data.bin.zst` или `data.tar`). Не учитываются `snapshot.yaml`, поддиректория
`snapshots/` со всеми дочерними узлами и файлы в `manifests/`, имена которых не оканчиваются на `.yaml`.

1. Для каждого учитываемого файла рассчитайте `sha256(<PATH> + 0x00 + <FILE_BYTES>)`. Путь указывается относительно
   директории узла в кодировке UTF-8, например `manifests/configmap_app.yaml` или `data.bin`. После пути добавьте один
   нулевой байт, затем байты файла без изменений.
1. Отсортируйте пути учитываемых файлов побайтово.
1. В полученном порядке передайте в итоговый расчёт SHA-256 сырые 32 байта контрольной суммы каждого файла.
1. Запишите полученное значение в `checksum.hex` в шестнадцатеричном виде в нижнем регистре.

**`childrenChecksum` — точный набор прямых дочерних узлов.** В один SHA-256 подаются по порядку:

1. Передайте ASCII-строку `d8-snapshot-children-checksum-v1` и один нулевой байт.
1. Передайте число прямых дочерних узлов десятичной строкой с префиксом длины.
1. Для каждого дочернего узла в каноническом порядке, описанном ниже, передайте семь значений из его `snapshot.yaml`,
   каждое — строкой с префиксом длины:

   - `apiVersion`;
   - `kind`;
   - `namespace`;
   - `name`;
   - `uid`;
   - `checksum.hex`;
   - `childrenChecksum.hex`.

**Строка с префиксом длины** означает, что сначала передаётся длина строки в байтах UTF-8 как восьмибайтовое целое число
в формате big-endian, а затем — сами байты. Если `namespace` или `uid` отсутствует, используется пустая строка: нулевая
длина без последующих байтов.

Для канонического порядка дочерние узлы сортируются по значениям полей `apiVersion`, `kind`, `namespace`, `name` и
`uid`, объединённым байтом `0x1F` в указанном порядке. Сравнение выполняется побайтово. Два дочерних узла с одинаковыми
значениями этих полей отклоняются.

Для узла без дочерних узлов рассчитывается контрольная сумма пустого набора. Её значение всегда равно
`926e82507890b7d5c7ad50f8cb7fd2172f81bfd2cf1d2ca86e3b644f66b02701`. Воспроизведение этой константы позволяет проверить
корректность реализации расчёта контрольной суммы.

Контрольные суммы дочерних узлов входят в контрольную сумму родительского узла, поэтому файлы `snapshot.yaml`
формируются снизу вверх, как описано [в разделе «Порядок сборки»](#порядок-сборки).

**`metadataChecksum` — контрольная сумма файла `snapshot.yaml`.** Файл сериализуется в компактный JSON без пробелов
между токенами, а поле `metadataChecksum` при этом полностью исключается. SHA-256 вычисляется от байтов этого JSON.
Порядок ключей фиксирован и не является алфавитным:

| Уровень | Порядок ключей | Исключаются при пустом значении |
|---|---|---|
| Верхний уровень файла | `formatVersion`, `apiVersion`, `kind`, `name`, `namespace`, `uid`, `sourceName`, `sourceObjectRef`, `checksum`, `childrenChecksum`, `volumes` | `formatVersion`, `namespace`, `uid`, `sourceName`, `sourceObjectRef`, `childrenChecksum`, `volumes` |
| Любая контрольная сумма | `algorithm`, `hex`, `short` | — |
| `sourceObjectRef` | `apiVersion`, `kind`, `name` | — |
| Запись `volumes` | `target`, `artifact`, `volumeMode`, `storageClassName`, `size`, `rawSizeBytes`, `storedSizeBytes` | `volumeMode`, `storageClassName`, `size`, `rawSizeBytes`, `storedSizeBytes` |
| `target`, `artifact` | `apiVersion`, `kind`, `name`, `namespace`, `uid` | `namespace`, `uid` |

Поля из столбца «Исключаются при пустом значении» не записываются в сериализованный JSON как `null`, а полностью
исключаются из него. Числа записываются десятичными целыми. В версии `2` в записи `volumes` нет ключей `rawSizeBytes` и
`storedSizeBytes`.

Это правило сериализации, а не список необязательных полей. `formatVersion` и `childrenChecksum` обязательны и должны
присутствовать в корректном файле. В корректном файле могут отсутствовать только `volumes` у узла без полезной нагрузки,
необязательные поля идентичности, а также `rawSizeBytes` и `storedSizeBytes` с нулевым значением. Остальные ключи записываются даже с пустыми значениями.

{{< alert level="warning" >}}
В строках экранируются `"` и `\`. Особое внимание следует уделять символам `<`, `>` и `&`: они экранируются как
`\u003c`, `\u003e` и `\u0026`. Всё остальное, включая не-ASCII, записывается как UTF-8.
{{< /alert >}}

Пример [из раздела «Файл `snapshot.yaml`»](#файл-snapshotyaml) даёт при расчёте ровно тот `metadataChecksum`, который в
нём указан, поэтому его можно использовать для проверки своей реализации этой сериализации.

## Проверка архива до загрузки

Для локальной проверки архива выполните команду:

```shell
d8 snapshot local describe <DIRECTORY>
```

где `<DIRECTORY>` — путь к директории архива.

Для выполнения команды кластер не требуется, а содержимое архива не изменяется.

Команда проверяет:

- все три контрольные суммы каждого узла;
- поля `snapshot.yaml` по описанным выше правилам;
- соответствие `volumes` полезной нагрузке, расположенной на диске.

Команда читает каждый байт полезной нагрузки, поскольку она входит в контрольную сумму содержимого узла. Поэтому
команда читает архив целиком и рассчитывает контрольные суммы SHA-256, в том числе для многотерабайтных томов. Проверка
может занять много времени.

Команда не проверяет:

- соответствие `rawSizeBytes` и `storedSizeBytes` полезной нагрузке;
- содержимое `data.tar`;
- фреймы zstd;
- наличие обязательной полезной нагрузки у узла VolumeSnapshot;
- вид корневого узла архива;
- упаковку в `.zip`, поскольку команда проверяет директорию на диске.

Успешная проверка не гарантирует, что архив удастся загрузить. Например, команда успешно проверит архив с обычным
tar-архивом или файлом `data.bin.zst`, сжатым через конвейер, но `d8` или веб-интерфейс
отклонят такой архив при загрузке.

## Упаковка дерева в .zip-архив

Файл `.zip` содержит то же дерево в упакованном виде. Структура дерева внутри него не меняется: путь записи
соответствует пути файла в дереве, а в качестве разделителя используется только `/`.

Большинство требований к `.zip` веб-интерфейс проверяет при открытии архива. Нарушение любого из них приводит к
отклонению всего архива.

При создании `.zip` соблюдайте следующие требования:

- Имя файла должно оканчиваться на `.zip` в любом регистре.
- Архив должен содержать ровно одну директорию верхнего уровня — директорию корневого узла. Создайте для неё отдельную
  запись директории, даже если корень можно определить по пути `<ROOT>/snapshot.yaml`.
- Пути записей должны быть уникальными. При повторении пути веб-интерфейс не сообщает об ошибке, а использует
  последнюю соответствующую запись центрального каталога, поэтому изменение файла может остаться незамеченным.
- Каждая запись должна использовать метод `stored`: метод сжатия `0` и в локальном заголовке, и в центральном каталоге,
  а размер записи в архиве должен совпадать с размером данных. Сжатая запись отклоняется независимо от её размера.
- Записи не должны быть зашифрованы ни обычным, ни усиленным шифрованием.
- Архив должен состоять из одной части: номера дисков равны `0`, число записей в записи конца центрального каталога
  совпадает с общим числом записей, а локатор ZIP64 не указывает на вторую часть.
- Имена записей должны быть корректными строками UTF-8. Если имя содержит байт `0x80` или выше, должен быть установлен
  флаг UTF-8 (бит 11). Этот флаг можно устанавливать для всех записей, включая записи с ASCII-именами.
- Пути записей не должны начинаться с `/` и содержать сегменты `..` и `.`, пустые сегменты, букву диска, обратный слеш,
  символы с кодом ниже `0x20` и символ `0x7f`.
- Локальный заголовок записи должен соответствовать её записи в центральном каталоге: совпадают байты имени, метод
  сжатия и состояние флага `data descriptor` (бит 3). Размеры и `crc32` можно передать в `data descriptor` после данных
  записи. В этом случае фактические размеры должны быть указаны в центральном каталоге: веб-интерфейс берёт их только
  оттуда.
- Запись директории должна оканчиваться на `/` и иметь нулевую длину и в архиве, и в данных. Директория с содержимым
  восстанавливается по путям вложенных записей, поэтому отдельная запись нужна только для пустой директории: без неё
  веб-интерфейс не отличит пустую директорию от несуществующей.
- Если поле содержит предельное значение — `0xFFFFFFFF` для 32-битных полей или `0xFFFF` для поля числа записей, —
  фактическое значение должно быть указано в структуре ZIP64: в extra-поле `0x0001` записи и в записи ZIP64 конца
  центрального каталога с локатором.
- Число записей в центральном каталоге должно совпадать с объявленным. Данные записей не должны заходить в центральный
  каталог. Запись конца центрального каталога должна завершать файл, а объявленная длина комментария — точно доходить до
  конца файла. Корректный непустой комментарий веб-интерфейс принимает, но при создании архива не добавляйте
  комментарий и никаких данных перед первой записью, включая самораспаковывающийся стаб.

{{< alert level="info" >}}
Значение `crc32` в центральном каталоге не сверяется с данными. Целостность архива проверяется с помощью трёх
[контрольных сумм SHA-256](#как-считаются-контрольные-суммы), а не средствами ZIP-контейнера.
{{< /alert >}}

## Где определён формат

Описанный формат дерева директорий реализован в `d8` и веб-интерфейсе Deckhouse. HTTP API модуля, описанный [на
странице «Интеграция с системами резервного копирования»](backup_integration.html), не задаёт формат файлов на диске.
Пример работы с архивом через `d8` приведён [на странице «Работа со снимками»](user_guide.html). При изменении формата
изменяется значение `formatVersion` в `snapshot.yaml`.

Для дескриптора `snapshot.yaml`, его канонической формы и трёх контрольных сумм в этом репозитории есть эталонная
реализация — Go-пакет `snapshotarchive` модуля в каталоге `api/`. Этот код общий для клиента `d8` и продукта резервного
копирования на Go, поэтому для одного и того же дерева они вычисляют одинаковый дескриптор и одинаковые контрольные суммы.
Пакет не выполняет ввод-вывод: какие файлы узла покрывает `checksum`, полезная нагрузка, `data.tar` и контейнер `.zip`
описаны выше. Эталонные векторы в `api/snapshotarchive/snapshotarchivetest` служат проверкой для реализации на любом другом
языке: дерево архива из пяти узлов с ожидаемыми контрольными суммами каждого узла и отдельные дескрипторы с точным
каноническим JSON, по которому вычисляется их `metadataChecksum`. Если эта страница и пакет расходятся в описании
дескриптора или контрольной суммы, верным считается пакет и его векторы.

Чтобы проверить остальную часть формата в своей реализации, запустите `d8 snapshot local describe` на созданном дереве директорий. Проверьте
загрузку с помощью `d8 snapshot upload` в подходящий целевой неймспейс. Повторите проверки после обновления клиента.
