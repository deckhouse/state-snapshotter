Модуль `state-snapshotter` позволяет создавать снимки состояния неймспейса и использовать сохранённое состояние для
последующего чтения или восстановления.

## Обзор снимков

Снимок создаётся после появления объекта [Snapshot](cr.html#snapshot-v1alpha1-spec) в кластере. Снимок фиксирует желаемое состояние неймспейса на определённый момент времени. Модуль захватывает манифесты
пользовательских объектов и сохраняет их в неизменяемом виде для последующего чтения или восстановления. Состояние неймспейса захватывается один раз. Для создания нового снимка создайте новый объект Snapshot.

## Принцип работы снимков

При создании снимка модуль:

1. **Определяет** все namespaced-ресурсы в кластере через API обнаружения Kubernetes, а не по фиксированному списку.
   Поэтому захватываются и произвольные кастомные ресурсы.
1. **Планирует захват** объектов неймспейса. Для объектов, снимками которых управляют другие модули, создаёт дочерние
   снимки. Остальные объекты отбирает по правилам из раздела [«Что попадает в снимок»](#что-попадает-в-снимок).
1. **Захватывает и сохраняет** манифесты и, где предусмотрено, данные томов. Хранение данных после удаления Snapshot
   описано в разделе [«Жизненный цикл и срок хранения»](#жизненный-цикл-и-срок-хранения).
1. **Публикует статус** готовности снимка. Проверка состояния описана в разделе
   [«Отслеживание статуса»](#отслеживание-статуса).

Если какой-либо вид ресурса нельзя прочитать, модуль не создаёт частичный снимок. Snapshot не достигает состояния
`Ready=True`, а попытка захвата повторяется, пока ресурс не станет доступен для чтения. Так бывает, если права RBAC
ещё не применены или агрегированный API недоступен.

Модуль записывает причину [в `status.captureState.domainSpecificController.message`](cr.html#snapshot-v1alpha1-status-capturestate-domainspecificcontroller-message)
и в событие типа `Warning` с причиной `NamespacePlanUnreadable`.

### Снимки, управляемые другими модулями

Для некоторых объектов Kubernetes одного манифеста недостаточно, чтобы восстановить их состояние. Модуль, который
управляет такими объектами, может определить собственный тип снимка и его состав. Для этого модуль регистрирует
соответствие между видом исходного объекта и типом снимка через
[CustomSnapshotDefinition](cr.html#customsnapshotdefinition-v1alpha1-spec). `state-snapshotter` использует определение,
только если для его текущего поколения установлены условия `Accepted=True` и `AccessGranted=True`.

Например, модуль [`virtualization`](/modules/virtualization/) может объявить VirtualMachineSnapshot типом снимка для объектов VirtualMachine. При
планировании `state-snapshotter` создаёт для каждой виртуальной машины (ВМ) дочерний VirtualMachineSnapshot. Затем
модуль `virtualization` определяет состав этого снимка. В него могут входить манифест VirtualMachine, манифесты и данные
подключённых VirtualDisk, манифесты Secret с настройками cloud-init и манифесты других связанных объектов, например
объектов подключения дисков или назначения IP-адресов. Конкретный состав зависит от реализации модуля `virtualization`.

Если для вида объекта нет CustomSnapshotDefinition, удовлетворяющего указанным выше условиям, `state-snapshotter` не
создаёт дочерний снимок для объектов этого вида. Обычный захват неймспейса может сохранить манифест объекта, а
связанные объекты захватываются по общим правилам: через собственные дочерние снимки, если для их видов есть такие
определения, либо как манифесты неймспейса и снимки томов PVC. Поэтому сохранённый манифест VirtualMachine не
гарантирует сохранения полного состояния ВМ.

Если объект уже охвачен дочерним снимком, например диск в составе VirtualMachineSnapshot, отдельный дочерний снимок для
него не создаётся. Корневой Snapshot сохраняет манифесты неймспейса, которые ещё не захвачены дочерними снимками. При
отборе объектов учитывается лейбл исключения. Подробнее — в разделе
[«Исключение объектов из снимка»](#исключение-объектов-из-снимка).

## Что попадает в снимок

В снимок попадают объекты целевого неймспейса, если они не исключены встроенными правилами или явно. Объекты с
собственной логикой снимка захватываются через дочерние снимки соответствующих модулей. Как исключить объект, описано в
разделе [«Исключение объектов из снимка»](#исключение-объектов-из-снимка). Отдельного списка включения объектов нет.

Таблицы ниже описывают автоматический отбор манифестов неймспейса. Состав дочерних снимков определяют соответствующие
модули, поэтому эти таблицы не охватывают все правила их захвата.

**Попадает (примеры):**

| Категория | Примеры |
|-----------|---------|
| Объекты конфигурации и данных | ConfigMap, Secret, Service, PersistentVolumeClaim (PVC), ServiceAccount, отдельный Pod |
| Рабочие нагрузки верхнего уровня | Deployment, StatefulSet, DaemonSet, Job, CronJob |
| Кастомные ресурсы | Кастомные ресурсы неймспейса |
| Сеть и RBAC | Ingress, NetworkPolicy, Role, RoleBinding |

Отдельный Pod захватывается, только если у него нет контроллера-владельца. Для сохранения манифестов модуль отбирает
виды ресурсов, поддерживающие операции `get`, `list` и `watch`. Ресурсы агрегированных API с постоянным хранилищем тоже
могут захватываться, если удовлетворяют этому условию. Secret типа `kubernetes.io/service-account-token` и
`ServiceAccount/default` не захватываются.

**Не попадает:**

| Категория | Примеры | Причина исключения |
|-----------|---------|--------------------|
| Объекты под управлением контроллера | Объекты с `ownerReference.controller: true` | Контроллер пересоздаёт их при восстановлении |
| Служебные объекты Kubernetes и CNI | Event, Endpoints, Lease, CiliumEndpoint, `ConfigMap/kube-root-ca.crt` | Создаются заново компонентами control plane или CNI и не относятся к пользовательскому желаемому состоянию |
| Вычисляемые объекты | PodMetrics, NodeMetrics и объекты API метрик без `watch` | Не сохраняются и не могут быть восстановлены |
| Служебные объекты снимков | CSI VolumeSnapshot и объекты зарегистрированных типов снимков, независимо от того, кто их создал | Исключаются, чтобы не захватывать служебные объекты самого механизма снимков |
| Объекты под управлением Deckhouse Platform | Объекты с лейблом `heritage: deckhouse` или `heritage: multitenancy-manager` | Создаются и восстанавливаются модулями Deckhouse Platform |
| Служебные объекты модуля | Группа `state-snapshotter.deckhouse.io` и виды запросов и передачи данных группы `storage-foundation.deckhouse.io` | Используются для внутренних операций |
| Операции резервного копирования | Backup, BackupPlan и BackupRestore модуля `backup` (группа `storage.deckhouse.io`) | После восстановления они запустились бы снова против восстановленного неймспейса |

К объектам под управлением контроллера относятся, например, ReplicaSet, созданные Deployment, и Pod, созданные этими
ReplicaSet. Среди вычисляемых объектов без поддержки `watch` — ресурсы API `metrics.k8s.io`, `custom.metrics.k8s.io` и
`external.metrics.k8s.io`. Виды запросов и передачи данных группы `storage-foundation.deckhouse.io` — VolumeCaptureRequest,
VolumeRestoreRequest, DataExport и DataImport.

Объекты с лейблом `heritage: deckhouse` или `heritage: multitenancy-manager` в снимок не попадают: их создают модули
Deckhouse Platform. Остальные объекты неймспейса, включая объекты, настроенные поверх модулей, считаются желаемым
состоянием и попадают в снимок.

### Исключение объектов из снимка

Снимок охватывает состояние неймспейса целиком. Чтобы объект не попал в снимок, добавьте ему лейбл
`state-snapshotter.deckhouse.io/exclude` **до** создания снимка. Захват выполняется один раз, поэтому добавление лейбла
после создания снимка не изменяет его содержимое:

```shell
d8 k -n myns label configmap scratch-cache state-snapshotter.deckhouse.io/exclude=""
```

{{< alert level="info" >}}
Значение лейбла не учитывается: объект исключается при любом значении, в том числе `false`. Чтобы снова включать объект
в снимки, удалите лейбл.
{{< /alert >}}

Лейбл исключения учитывается на нескольких уровнях дерева снимка, но за исключение отвечают разные участники:

- **Обычный объект**, например ConfigMap или Secret, исключается из захваченных манифестов неймспейса.
- **Объект, для которого предусмотрен отдельный тип снимка**, например VirtualMachine, исключается при планировании.
  Если на объекте VirtualMachine установлен лейбл, соответствующий VirtualMachineSnapshot не создаётся.
- **За исключение объекта внутри дочернего снимка**, например VirtualDisk или Secret ВМ, отвечает модуль, который
  формирует этот снимок.
- **PVC, не охваченные дочерними снимками других модулей**, при наличии лейбла исключения не попадают в снимок ни как
  манифесты, ни как данные томов. Пользовательский CSI VolumeSnapshot для такого PVC остаётся обычным CSI-снимком,
  модуль не принимает его под управление.

Сам `state-snapshotter` обеспечивает исключение для объектов верхнего уровня с собственным типом снимка, манифестов
неймспейса и PVC, не охваченных дочерними снимками других модулей.

**Исключение не наследуется.** Если на объекте VirtualMachine установлен лейбл исключения, `state-snapshotter` не
создаёт для него VirtualMachineSnapshot. Связанные VirtualDisk, PVC, Secret и другие объекты при этом не исключаются
автоматически. Они могут попасть в снимок через собственные дочерние снимки либо как манифесты неймспейса и снимки томов
PVC. Чтобы исключить их, добавьте лейбл каждому из них.

**Часть исключений фиксируется в статусе.** Объекты с собственным типом снимка, например VirtualMachine, и объекты,
которые модули исключили внутри своих дочерних снимков, перечисляются в
[`status.excludedRefs`](cr.html#snapshot-v1alpha1-status-excludedrefs) корневого Snapshot. В этом поле отображаются не
все исключения: например, ConfigMap, исключённый при отборе манифестов, в нём не указывается. Отсутствие записи не
означает, что лейбл не учтён.

**Лейбл, как и встроенные исключения, позволяет только исключать объекты из захвата.** Отдельного механизма включения
объектов в снимок нет: снимок содержит объекты неймспейса, кроме исключённых. Чтобы получать снимки с разным набором
объектов, используйте разные неймспейсы.

## Необходимые права

Начиная с Deckhouse Platform 1.78, роли неймспейса предоставляют следующие права:

| Роль | Операции со снимками |
|---|---|
| `viewer` | Просмотр снимков и их статусов |
| `manager` | Создание снимков и скачивание манифестов, но не передача данных томов |
| `admin` | Загрузка и восстановление снимков, передача данных томов. Нужна для полного скачивания и загрузки снимков через `d8` |

Данные томов передаются через модуль [`storage-foundation`](/modules/storage-foundation/), поэтому для скачивания или загрузки снимка с томами также
нужна его capability `transfer_volume_data` (именованный набор прав модуля, который выдаётся отдельной ClusterRole).
В роль `manager` она не входит. Начиная с Deckhouse Platform 1.78,
capability входит в роль неймспейса `admin`. Чтобы выдать её без роли `admin`, привяжите в неймспейсе ClusterRole
`d8:namespace-capability:storage-foundation:transfer_volume_data`. В Deckhouse Platform с 1.76.9 по 1.77 capability не
входит в пользовательские роли неймспейса: привяжите в неймспейсе ClusterRole
`d8:use:capability:module:storage-foundation:transfer_volume_data`.

Команде `d8 snapshot restore` нужны следующие права:

- Для применения объектов приложения: `patch` на существующие объекты и `create` на создаваемые объекты
  соответствующих типов. Объекты, кроме PVC, команда создаёт через Server-Side Apply, а отсутствующие PVC создаёт
  отдельно. Одного права `update` недостаточно.
- Для проверок восстановления: `get` на PVC, дочерние снимки томов и PersistentVolume.
- Для параметра `--wait`: `get` на StorageClass, `list` на StorageClass для поиска класса по умолчанию, а также `list`
  на Pod и Event при проверке томов с режимом `WaitForFirstConsumer`.

Назначайте эти права в целевом неймспейсе или на уровне кластера в зависимости от типа объекта.

## Создание снимка

Создайте Snapshot в неймспейсе, состояние которого нужно захватить:

```shell
d8 snapshot create my-namespace-snapshot -n my-app --wait
```

С параметром `--wait` команда ждёт, пока Snapshot не перейдёт в состояние `Ready`. Без него команда завершается сразу
после создания объекта, а готовность можно отследить, как описано [в разделе «Отслеживание статуса»](#отслеживание-статуса).

Команда создаёт Snapshot, равнозначный следующему. Такой же объект можно создать командой `d8 k apply`:

```yaml
apiVersion: state-snapshotter.deckhouse.io/v1alpha1
kind: Snapshot
metadata:
  name: my-namespace-snapshot
  namespace: my-app
spec: {}
```

Спецификация Snapshot неизменяема. Пустая спецификация `spec: {}` запускает динамический захват состояния неймспейса, в
котором создан Snapshot. В примере это `my-app`. Режим по умолчанию:
[`spec.mode`](cr.html#snapshot-v1alpha1-spec-mode) `Capture`. Указывать целевой неймспейс отдельно не нужно.

{{< alert level="warning" >}}
Не используйте параметр `-l`/`--selector` команды `d8 snapshot create`: Snapshot всегда захватывает весь неймспейс, и
API-сервер отклоняет Snapshot с селектором ресурсов. Чтобы исключить объекты из снимка, добавьте им лейбл, как описано
[в разделе «Исключение объектов из снимка»](#исключение-объектов-из-снимка).
{{< /alert >}}

## Режимы снимка

Источник содержимого Snapshot задаёт поле `spec.mode`. Оно неизменяемо, как и вся спецификация:

| Режим | `spec` | Поведение |
|-------|--------|-----------|
| `Capture` (по умолчанию) | `spec: {}` или явное `spec.mode: Capture` | Модуль захватывает текущее состояние неймспейса |
| `Import` | `spec.mode: Import` | Snapshot получает содержимое из ранее скачанного снимка. Объекты неймспейса не захватываются |

Создавать Snapshot в режиме `Import` вручную не нужно: его создаёт команда `d8 snapshot upload`, как описано
[в разделе «Перенос снимка в другой неймспейс или кластер»](#перенос-снимка-в-другой-неймспейс-или-кластер).

## Отслеживание статуса

Используйте следующую команду, чтобы посмотреть снимки в целевом неймспейсе:

```shell
d8 k -n my-app get snap
```

Пример вывода:

```console {.nowrap-default}
NAME                    READY   REASON      CONTENT                        AGE
my-namespace-snapshot   True    Completed   nss-content-1f4b0c9d2a3e5f76   30s
```

Чтобы просмотреть определённый снимок и его дерево, выполните команду:

```shell
d8 snapshot describe my-namespace-snapshot -n my-app
```

Подробная информация о захваченном состоянии содержится [в поле
`status.conditions`](cr.html#snapshot-v1alpha1-status-conditions):

```shell
d8 k -n my-app get snap my-namespace-snapshot -o jsonpath='{.status.conditions}' | jq
```

Снимок готов, когда условие `Ready` имеет значение `True` с reason `Completed`. Только это сочетание означает, что
захват завершён и его результат сохранён. Пока поле
[`status.boundSnapshotContentName`](cr.html#snapshot-v1alpha1-status-boundsnapshotcontentname) пустое, скачать снимок
нельзя.

Если условие `Ready` имеет значение `False`, действуйте в зависимости от reason:

| Reason | Что это значит | Что делать |
|---|---|---|
| `ArtifactMissing`, `ChildSnapshotLost`, `ChildrenFailed`, `CreateChildFailed`, `DomainCaptureFailed`, `DuplicateCoveredPVCUID`, `GraphPlanningFailed`, `ListFailed`, `ManifestCheckpointFailed`, `NamespaceNotFound`, `VolumeCaptureFailed` | Захват завершился ошибкой и не будет повторён. Снимок не станет готовым | Прочитайте сообщение условия, устраните причину, удалите Snapshot и создайте новый |
| `ChildSnapshotDeleted` | Объект узла дерева удалён. Сохранённые данные не потеряны, но снимок находится в деградированном состоянии и сам не восстановится | Если нужен полный снимок, создайте новый. Чтобы избежать такого состояния, не удаляйте узлы дерева напрямую, см. [раздел «Защита от удаления»](#защита-от-удаления) |
| Любой другой reason | Захват выполняется | Дождитесь завершения. Если статус долго не меняется, проверьте сообщение условия и события Snapshot |

Если захват ожидает тип ресурсов, который не удаётся прочитать, например из-за ещё не применённых прав RBAC, причина
указывается [в поле
`status.captureState.domainSpecificController.message`](cr.html#snapshot-v1alpha1-status-capturestate-domainspecificcontroller-message)
и в событии `Warning` с reason `NamespacePlanUnreadable`. Подробное значение каждого reason приведено [в разделе
«Проверка состояния снимка»](backup_integration.html#проверка-состояния-снимка).

## Восстановление снимка

Команда `d8 snapshot restore` применяет захваченные объекты приложения в неймспейсе, где находится готовый Snapshot.
Сначала проверьте, что восстанавливаемые манифесты можно применить, не сохраняя изменения:

```shell
d8 snapshot restore my-namespace-snapshot -n my-app --dry-run
```

С параметром `--dry-run` API-сервер Kubernetes проверяет манифесты валидацией и admission-проверками, но не сохраняет
их. Команда не показывает различия между текущими и восстанавливаемыми объектами. Перед восстановлением без
`--dry-run` отдельно проверьте восстанавливаемые манифесты и существующие объекты. Затем восстановите объекты
приложения:

```shell
d8 snapshot restore my-namespace-snapshot -n my-app --wait
```

Команда подготавливает захваченные манифесты и применяет их без исходных служебных метаданных.
Восстанавливаемые PVC ссылаются на соответствующие снимки томов через `PersistentVolumeClaim.spec.dataSourceRef`.
Драйвер хранилища создаёт тома с данными из этих снимков.
С параметром `--wait` команда ждёт, пока соответствующие PVC перейдут в состояние `Bound`. Готовность приложения
команда не проверяет.

Направить восстановление непосредственно в другой неймспейс нельзя. Для другого неймспейса или кластера выполните
действия [из раздела «Перенос снимка в другой неймспейс или кластер»](#перенос-снимка-в-другой-неймспейс-или-кластер).
Не создавайте вручную служебные объекты модуля, например VolumeRestoreRequest.

Внешние клиенты могут получить подготовленные манифесты без их применения через эндпоинт, описанный
[в разделе «Чтение снимка для восстановления»](backup_integration.html#чтение-снимка-для-восстановления).
Эндпоинт только возвращает объекты, а `d8 snapshot restore` также применяет их.

## Перенос снимка в другой неймспейс или кластер

Снимок переносится через директорию на машине, где запускается `d8`: вы скачиваете снимок из исходного неймспейса,
загружаете в целевой неймспейс и восстанавливаете в нём. Скачанную директорию можно также хранить как копию вне
кластера: в этом случае выполните шаги 1 и 2 сейчас, а остальные — когда потребуется восстановление.

Чтобы перенести снимок, выполните следующие шаги:

1. Скачайте готовый снимок:

   ```shell
   d8 snapshot download my-namespace-snapshot -n my-app -o ./my-snapshot
   ```

   Команда скачивает всё дерево снимка, включая захваченные манифесты и данные томов, а не только объекты корневого
   узла. При запуске вне кластера команда сама выбирает способ доступа к экспортёру томов. Для
   опубликованного эндпоинта необходима аутентификация по токену.

1. Проверьте скачанную директорию без подключения к кластеру:

   ```shell
   d8 snapshot local describe ./my-snapshot
   ```

   Что проверяет эта команда и чего она не проверяет, описано [в разделе
   «Проверка архива до загрузки»](snapshot_archives.html#проверка-архива-до-загрузки).

1. Загрузите директорию в целевой неймспейс. Для другого кластера используйте контекст подключения к нему:

   ```shell
   d8 snapshot upload -n my-app-restored -i ./my-snapshot
   ```

   Целевой неймспейс должен существовать. Используйте неймспейс без конфликтующих объектов приложения. Параметр `-i`
   принимает директорию, а не ZIP-файл. Команда создаёт Snapshot в режиме `Import` и воссоздаёт его дерево, включая
   снимки томов и данные томов. Состояние целевого неймспейса команда не захватывает, а манифесты приложения не
   применяет.

1. Проверьте готовность загруженного Snapshot, как описано [в разделе «Отслеживание статуса»](#отслеживание-статуса):

   ```shell
   d8 snapshot describe my-namespace-snapshot -n my-app-restored
   ```

1. Восстановите объекты приложения в целевом неймспейсе, как описано
   [в разделе «Восстановление снимка»](#восстановление-снимка):

   ```shell
   d8 snapshot restore my-namespace-snapshot -n my-app-restored --dry-run
   d8 snapshot restore my-namespace-snapshot -n my-app-restored --wait
   ```

Структура архива и требования совместимости описаны [на странице
«Работа с архивами снимков»](snapshot_archives.html). Для разработчиков собственных систем резервного копирования
контракт API узлов и правила определения размера томов описаны [на странице
«Интеграция с системами резервного копирования»](backup_integration.html).

## Жизненный цикл и срок хранения

Жизненный цикл снимка определяется его неизменяемостью и сроком хранения сохранённых данных после удаления объекта
Snapshot:

- **Одноразовый / неизменяемый.** Спецификация фиксируется при создании. `metadata.generation` не увеличивается,
  повторного захвата нет.
- **Хранение после удаления.** После удаления Snapshot сохранённые данные хранятся в течение срока, заданного
  параметром модуля [`snapshotTtlAfterDelete`](configuration.html#parameters-snapshotttlafterdelete) (по умолчанию
  30 дней), и затем удаляются.
- **Нет фоновой нагрузки.** Модуль захватывает состояние только в ответ на явные запросы. Непрерывного фонового
  захвата нет; по расписанию выполняется только удаление данных с истёкшим сроком хранения.

### Удаление снимка

Чтобы удалить снимок целиком, удалите корневой Snapshot:

```shell
d8 snapshot delete my-namespace-snapshot -n my-app --wait
```

С параметром `--wait` команда ждёт, пока модуль не удалит Snapshot и его дерево. Дочерние узлы дерева модуль удаляет
вместе с корневым Snapshot. Сохранённые данные хранятся в течение срока, заданного параметром
`snapshotTtlAfterDelete`, как описано выше. Не удаляйте дочерние узлы напрямую: они защищены, как описано
[в разделе «Защита от удаления»](#защита-от-удаления).

### Защита от удаления

Внутренние объекты дерева снимка защищены от случайного прямого удаления admission-политикой (delete-guard). Без неё
удаление дочернего объекта, например управляемого CSI VolumeSnapshot, через веб-интерфейс Deckhouse переводит корневой
Snapshot в деградированное состояние. Сохранённые данные при этом остаются.

Защита работает следующим образом:

- **Что защищено.** Объекты в неймспейсе, представляющие узлы дерева: дочерние Snapshot и управляемый CSI VolumeSnapshot.
  Они содержат лейбл `state-snapshotter.deckhouse.io/delete-protected: "true"`.
- **Что НЕ защищено.** Корневой Snapshot не имеет этого лейбла: удаление корневого Snapshot — штатный способ удалить
  всё дерево. Лейбл также не устанавливается на следующие cluster-wide-объекты:
  - SnapshotContent;
  - ManifestCheckpoint и его чанки;
  - ObjectKeeper;
  - управляемый CSI VolumeSnapshotContent.

  Прямое удаление этих объектов не блокируется admission-политикой и может привести к деградации дерева снимка. На
  объекты вне дерева снимка эта защита не распространяется.
- **Принудительное удаление.** Чтобы удалить защищённый объект напрямую, установите аннотацию
  `deckhouse.io/allow-delete: "true"`, затем удалите объект. Обычный пользователь не может удалить или изменить сам
  лейбл. Аннотация — единственный поддерживаемый способ обхода защиты. Аннотацию можно снять, пока объект не удалён.
- **Защита включена всегда.** Параметра модуля для отключения или ослабления защиты нет. Для исключительного прямого
  удаления используйте указанную выше аннотацию.

## Замечания и ограничения

При работе со снимками учитывайте следующие ограничения:

- Snapshot захватывает объекты только своего неймспейса. Единственный cluster-wide-объект, который включается в
  снимок, — соответствующий объект Namespace.
- Манифесты сохраняются в исходном виде, включая `status`. Служебные поля, такие как `status`, `resourceVersion` и
  `uid`, удаляются только при чтении манифестов для восстановления.
- Объекты Secret сохраняются в исходном виде. Исключение составляют Secret с токенами ServiceAccount — они не включаются
  в снимок согласно правилам захвата.
